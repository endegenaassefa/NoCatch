Give a 90 minute session its own materials

Let a user add five to ten slide decks before a session, show exactly what was read, retrieve relevant passages for each question, and clear app-owned content at the session deadline. The feature needs one module responsible for material ownership, import, retrieval, and expiration.

What is ready for review

A researched architecture, an interactive product prototype, and a runnable storage experiment. This is a design package; the production NoCatch app and installer have not been changed. Local PPTX/PDF upload is the agreed first release. Answers may use general knowledge, clearly distinguished from cited materials. Timer start and restart recovery remain proposed defaults pending the user's selections.

What the user sees

During first setup, place Add material for this session after account connection and before the first question. It is optional. During later launches, a new session opens the same material preparation screen; an existing session shows Resume session — 23 minutes left. Do not repeat account setup or hide a recovered deadline.

Connect accountExisting setup
Add materialOptional PowerPoint or PDF
Review what was readText, notes, visual gaps
Start session90 minutes from this action
Ask and inspect sourcesMaterial citations plus labeled general knowledge

The preparation screen has a file picker and drop area, a file list with individual status, remaining capacity, a short retention explanation, and explicit consent to send relevant excerpts to the selected AI provider. Use Start 90 minute session and Continue without materials as the main actions. Chat gets a compact Materials · 5 ready · 73:10 remaining control; it opens the same screen.

Each file progresses through Queued → Reading → Indexing → Ready, with separate Partially read, Failed, and Cancelled states. A partial result might say, “42 of 60 slides read; 18 image or diagram slides need visual processing.” The user can preview text, inspect coverage, remove a file, and retry by selecting a corrected copy. Failed files do not contribute context.

Start is enabled with at least one ready or partially read material and consent; starting without material is always available. If some imports are unfinished, explain that starting will cancel those jobs and retain only the accepted materials. Adding or removing a material later invalidates affected answer work and keeps the original deadline.

Google Slides users can choose File → Download → Microsoft PowerPoint (.pptx) or PDF and upload the copy. Direct Google selection is a later integration. The prototype's Google control explains the flow; it is not a working connector. The prototype accepts real file names and sizes for preview, but does not read their contents or persist anything across reloads.

The sharp questions and resulting choices

These questions come from thinking as the user, the engineer, and the product owner. Most are design decisions the engineer can make; the few that change the experience were sent to the user.

Capacity is four different budgets

“Ten decks” does not tell us the memory cost. Ten mostly text decks can be small; ten decks with high-resolution screenshots can be enormous. Use an understandable file limit while enforcing the actual expensive resources underneath it. The following are proposed initial limits, not measured production guarantees.

ResourceProposed limitReason
Original files10 accepted files; 50 MiB each; 250 MiB totalAllows typical five to ten deck preparation while bounding local reads. Failed/cancelled inputs release reservations. Repeated copies count once after hashing.
Slides or PDF pages250 per file; 1,000 per sessionBounds extraction and indexing work independently of compressed size.
Decoded text4 MiB per file; 16 MiB per session; 12,000 chunks maximumBounds durable payload and the searchable corpus. Stop with a clear capacity error instead of truncating silently.
Archive expansion5,000 entries; 300 MiB expanded per file; 8 MiB per XML entryDefense limits for an import process. Measure bytes actually inflated. Do not extract ZIP paths onto the filesystem.
Import concurrencyOne parser job at a time; at most 10 queued jobs; proposed 60 second parse deadlinePrevents ten decks from allocating parser memory at once. Large legitimate files can still fail visibly and be split.
Parser memoryProposed 256 MiB per isolated workerA target for enforcement and measurement. A V8 heap option alone does not bound native buffers or total process memory; use OS limits/monitoring and verify packaged behavior.
Material sent per answerAt most eight passages and 6,000 material tokens, also bounded to 24,000 charactersThe current managed server permits 32,000 total input characters. Reserve room for the user's question and recent conversation; shrink excerpts/history to fit the actual provider's budget.

The file and text budgets are fixed policy ceilings. Actual memory grows with accepted content; we do not allocate maximum capacity up front. Prompt selection is dynamic: include the passages useful for this question. Count tokens using the selected model's tokenizer or count API when available; a character estimate is a secondary guard, not an exact token count.

Explore a planning estimate

These are assumptions for capacity planning. File sizes and real token counts are not implied.

Token estimate = words × 1.33, a rough English planning assumption. The proposed page limit remains 1,000.

For ten decks × 60 slides × 180 words, the assumed corpus is 108,000 words, or roughly 144,000 tokens. Re-sending the whole corpus for twenty questions means about 2.9 million material-input tokens. A 6,000 token material budget for twenty questions is at most 120,000. This arithmetic motivates retrieval; it does not prove that retrieval finds all the required facts. No dollar estimate is made without the actual model, billing tier, and measured token counts.

Read the deck correctly

A PPTX is a package of XML and other files. Extract slide text in the presentation's declared order, using its relationship files; sorting slide1.xml, slide2.xml filenames is not a reliable presentation-order rule. Join text runs while preserving paragraph and table structure. Read speaker notes through slide relationships and label them separately. Do not include master-layout boilerplate or the notes page's slide-number placeholder as substantive content. Microsoft documents text and notes as separate presentation structures. Microsoft Open XML documentation.

Use a maintained ZIP/XML parser with external entity resolution disabled and actual output limits. A renamed file is not proof of format; verify the package or PDF signature and required structure. Never execute embedded content or fetch external links from a document. Reject encrypted or malformed inputs with a precise explanation. Old binary .ppt, macros, and animations are outside the first release; ask the user to save a PPTX/PDF copy.

For PDFs, preserve page numbers and extract text locally. Check actual text coverage rather than assuming every PDF has text. Scans and diagram-only pages need optical character recognition or visual interpretation. The first release must flag unsupported visual content; adding OCR later uses the same material module and coverage model. OCR can misread formulas and tables, so its output must retain its source page and extraction method.

Keep one chunk near a slide or coherent topic, splitting large notes or slides into roughly 500–800 token passages without losing source location. A chunk identifies its document, slide/page, title, extraction method, notes/text distinction, and content hash. Long table rows should keep their headers. Partial extraction is permitted only with visible coverage and no silent byte-limit truncation.

How the material reaches the AI

Retrieve using the current question and a small amount of recent conversation. Search locally, combine relevant passages within the material budget, and send a separate material field alongside the user question. The system instruction tells the model that material is evidence supplied by a user and may contain untrusted instructions. A slide saying “ignore previous rules” must not become a system instruction.

Start with SQLite full-text search, titles, neighboring slides, and a small glossary of course vocabulary. This is mechanically simple and matches exact terms well. It can miss synonyms and conceptual questions; do not advertise semantic understanding from a keyword index. Evaluate on representative deck questions before deciding whether to add local embeddings and a second retrieval stage. Keep both implementations behind the same retrieval interface.

Answers cite only source identifiers from the supplied passages. Use clickable file names and slide/page numbers; the source preview shows the original extracted passage, including whether it came from notes. A metadata check confirms that a source exists; it does not establish that a cited claim is entailed. Real evaluation must assess that relationship. When decks disagree, mention the disagreement and show both sources.

The user chose to allow general knowledge. Use phrasing such as “Your slides say…” and “From general knowledge…” when support differs. If no relevant passage is found, say the available material does not establish the answer, then give a clearly labeled general answer if useful. Avoid numeric confidence scores that have not been calibrated.

Text, voice, screenshots, and the setup question must all call the same material retrieval interface. For screenshot-only questions, obtain a text query through a scoped visual-reading stage before local retrieval, or request a typed question. Do not claim that a hardcoded “help me understand this image” retrieves the right course material. Do not push the entire deck corpus into the screenshot prompt as a fallback.

Where the content lives

Propose a session material directory under Electron's app.getPath('userData'), such as materials/<random-session-id>/. It is per user and independent of the installer, Desktop working directory, or install permissions. Read selected original files without modifying them. Prefer discarding raw uploaded bytes once extraction finishes; an encrypted temporary raw copy is permitted only while a conversion/import actually needs it.

Original fileRead only; remains user's property
Isolated import processBounded bytes, time, and memory
Encrypted SQLite payloadsRecover until original deadline
RAM search indexRebuilt from unexpired content
Bounded answer excerptsSame session and owner

Use one random encryption key per material session. Encrypt extracted payloads, filenames, previews, notes, and any persisted session answers with authenticated encryption, such as AES-256-GCM, using a fresh nonce for every encryption. Bind ciphertext to the session, owner, document, and chunk identifiers. Store the wrapped session key using Electron's OS-backed safeStorage. Keep the expiration metadata integrity-protected as well; encryption alone does not make a mutable deadline trustworthy.

The searchable full-text index is in an in-memory SQLite database, with temporary operations restricted to memory. Keeping only encrypted content in the durable database avoids a second plaintext search copy. SQLite warns that full-text shadow tables can retain forensic traces despite ordinary secure deletion. This design is an inference from that documented limitation, not a SQLite guarantee of erasure. SQLite secure_delete documentation.

On Windows, safeStorage uses DPAPI; its protection is against other users, and does not make the data inaccessible to every program running as the same user. On Linux, refuse persistent recovery if the selected safeStorage backend is basic_text; offer an explicitly described memory-only session instead. On macOS, consistent signing and Keychain behavior need native verification. Electron safeStorage documentation.

Deleting the wrapped key and encrypted files reduces recoverability in app-managed storage, but cannot prove physical erasure from SSDs, backups, snapshots, OS swap, or crash dumps. This app controls its own copies; it cannot erase the user's original PowerPoint, their Google Drive file, or an AI provider's retained requests. The retention copy must say precisely that.

Commit accepted document metadata and chunks in one durable transaction. Publish a searchable document only after successful commit. If rebuilding/updating the in-memory index fails, reconstruct it from the durable transaction or mark the document unavailable; do not leave a ready row that cannot be searched. Reserve capacity before launching a job, release it on failure/cancellation, and serialize mutation of session capacity.

A deadline needs a lifecycle

Draft preparation gets a maximum 30 minute lifetime from the first accepted import. Starting promotes the accepted material to a session ending 90 minutes later. Returning to the app, adding a file, refreshing credentials, or reading a source does not extend either deadline. These are proposed product rules, not an existing paid-session implementation in NoCatch.

Check expiration before import acceptance, parser commit, recovery/decryption, retrieval, answer dispatch, answer-delta delivery, history reads, and source preview. A periodic timer is only a cleanup trigger. A delayed timer cannot authorize data access after the deadline. Tie asynchronous work to a session generation so removed files, account changes, and expired sessions cannot publish stale results.

  1. At expiry or explicit End session, synchronously mark the material session unavailable and increment its generation.
  2. Cancel parser jobs and AI requests; reject late worker results and suppress answer deltas and response panels from that generation.
  3. Clear related conversation history, renderer previews, answers, drafts containing material text, and the RAM search index.
  4. Remove the wrapped key and app-owned encrypted database, sidecar journals, temporary copies, and thumbnails. Record content-free cleanup evidence.
  5. If unlinking fails, keep access blocked, retry cleanup, and show the actual failure. Never announce successful deletion while an app copy remains.

When the app or computer is off, no local timer can run. On the next launch, check metadata and delete expired content before attempting decryption. If exact physical deletion while the app is closed is essential, it requires a separately managed background agent or remote storage lifecycle; the installer and recovery behavior become part of the feature. A remote system also cannot make a powered-off local disk erase itself.

During a running session use both the UTC deadline and monotonic elapsed time. Suspend/resume triggers immediate revalidation. Across launches, local clocks and editable local state are insufficient for enforcing paid time against tampering. Managed paid sessions need a server-issued, owner-bound session grant and server-enforced deadline. If authoritative verification is unavailable, fail recovery closed or clearly narrow the offline guarantee; do not invent a payment entitlement from an access token.

Copies in the backend and provider

The current backend stores output text and stream events, with a default 24 hour retention. Outputs may quote a deck. Therefore, a material session needs its own shorter deadline carried through the managed answer contract; simply reducing local document retention would leave related backend answers behind.

Propose a transient answer path for material sessions: keep answer text and stream events in bounded RAM keyed by the authenticated owner and material session, and persist only content-free request/quota metadata. At expiry, cancellation, or service shutdown, remove that transient content. After a service restart, report the interrupted answer instead of recovering content from a plaintext durable store. If durable answer recovery is a requirement, add session-key encryption and the same deadline cleanup on the server.

The server validates the material field, source IDs, input size, owner, and session deadline. It controls the deadline for managed sessions and refuses expired work independently of the client. Quota/account access remains subject to existing server validation. No document bodies, excerpts, user drafts, or answers belong in logs or analytics. Inspect existing debug logging as part of the build; it currently includes text fields in several answer paths.

Send selected excerpts in ordinary answer requests rather than uploading whole decks to a provider file store. Gemini's Files API automatically removes files after 48 hours, which does not satisfy a 90 minute app lifecycle without explicit file deletion and retry tracking. Gemini Files API documentation.

Ordinary provider requests also have provider retention terms. Google's paid-service terms describe limited retention of prompts and responses for policy enforcement and legal/regulatory purposes. The UI can promise cleanup of app-controlled copies; it must not claim universal deletion from the provider after 90 minutes. Gemini API paid-service terms.

The module and integration plan

The public interface should stay small: status(), import(files), start(), retrieve(question), remove(documentId), and end(reason). The interface includes the deadline, owner checks, supported formats, bounded errors, and how partial content is reported. Importers, encrypted storage, the RAM search index, and cleanup are implementation details inside the module.

Use a production folder such as src/materials/ for that module. UI code should not operate SQLite, decrypt content, accept arbitrary filesystem paths from an untrusted frame, or invent session IDs. Electron main opens the native picker and passes selected files to the import process. Add narrow preload calls for status, import, session start/end, removal, and source preview. Verify every IPC sender using the existing trusted-renderer checks.

The working tree already contains substantial user changes. Implementation should preserve those changes and use a dedicated patch or branch after recording the current baseline. No installer was rebuilt for this design package.

Build order and release proof

  1. Session and storage. Implement owner binding, draft/session deadlines, encrypted recovery, capacity accounting, generation invalidation, and cleanup. Test exact expiry and interrupted writes through the public interface.
  2. Local extraction. Implement bounded PPTX and PDF workers, real slide/page order, notes, and honest visual coverage. Use real or licensed fixtures, including reordered, large, corrupt, and scanned files.
  3. Retrieval and answer contract. Wire text, setup, speech, and screenshot paths. Add a dedicated reference field; include token/character budgeting and source previews. Add the backend material-session contract and content retention behavior.
  4. Product UI. Connect the prototype's preparation, progress, partial/error, recovery, timer, source, and deletion behavior to actual module status. Test keyboard use and the real file picker on Windows.
  5. Quality and distribution. Evaluate at least 30 representative questions across five to ten real decks, including synonym, multi-deck, diagram-only, conflicting, and missing-answer questions. Require correct support for every shown citation, explicit gaps, and no privacy/expiry failures. Record actual extraction latency and peak RAM on a named Windows machine, then package and verify the installer.

Proposed performance targets to validate, rather than promises: ordinary local text lookup p95 under 100 ms; normal text-deck import under 10 seconds per file; visible cancellation within one second; no blocked renderer during import; expired access blocked at the first operation after the deadline. Visual processing needs its own measured targets.

Later direct Google selection

Use a registered Google OAuth application and Google's file Picker with the recommended drive.file scope. NoCatch account sign-in alone does not authorize reading Google Drive. Ask for selected-file access rather than the whole Drive, and preserve a local upload alternative. Google Drive scope guidance, Google Picker for desktop applications.

The Google Drive files.export endpoint limits exported content to 10 MB. A bigger deck needs a visible error and local-copy route, or a separately designed native Slides-content adapter. Do not silently lower the app's general file limit because one source adapter has a smaller export limit. Google export documentation.

What the experiment actually proved

Recorded storage results come from a runnable Node experiment using Node 24 on Linux/WSL and generated slide text. It creates actual encrypted SQLite rows and a RAM-only FTS5 index, closes/reopens them against a controlled clock, and checks plaintext canaries and exact-deadline rejection. It does not invoke the production NoCatch code.

All 13 assertions passed: three workloads each checked encrypted disk content, recovery with the same deadline, read/write rejection exactly at expiry, and deletion on expired startup; another check rejected modified ciphertext and the wrong session binding. Each workload also completed 60 unique-anchor retrievals with expected file/slide mapping. The rough token calculator omits those test anchors.

Process RSS ended near 58, 63, and 101 MiB across successive workloads. These are cumulative process snapshots, not isolated peak measurements or Windows app RAM figures. The measurements support feasibility of the storage shape; they do not measure ZIP extraction, PDFs, OCR, images, semantic relevance, native safeStorage, or full AI answers.

The experiment intentionally models a session that has already started. It does not implement draft promotion, production atomic disk/index updates, background cleanup, safeStorage key wrapping, server-owned deadlines, or account isolation. Its key is supplied by the test harness to reopen content. It is a proof of the mechanism, not code to plug into the app unchanged.

Browser interaction evidence records 27 successful checks. They cover consent, partial and failed material, removed-source citation behavior, downloaded Google copies, capacity messages, and mobile layout. A controlled browser clock also verified that returning after removal retains 80 minutes, that the real timer expires at 90 minutes, and that expiration clears an open source preview. Recovery remains a simulated UI state. These checks do not establish native Electron integration or the finished feature.

Remaining decisions and evidence

Implement the module and integrations above using the proposed clock-start and recovery behavior unless the user selects alternatives. The first release format scope and answer policy are already settled by the user. Exact physical deletion while a computer is off, universal provider deletion, and semantic answer correctness are not established by this package.
